# 概要

`HTSlib` は、ゲノムデータの読み書きに用いられ、
`samtools` および `bcftools` の基盤をなす C ライブラリである
[@Bonfield2021HTSlib; @Danecek2021SAMtools]。`hts.cr` と `ruby-htslib` は、
HTSlib をそれぞれ Crystal と Ruby から利用できるようにする。両ライブラリは、
SAM/BAM/CRAM、VCF/BCF、インデックス付き参照配列（Faidx）、Tabix で索引付けされた
ファイル、および pileup の生成をサポートする。

`ruby-htslib` は、システムにインストールされた HTSlib に直接リンクする Ruby 向けの
ネイティブ C 拡張を使用する。一方、`hts.cr` は Crystal の FFI を介して HTSlib を呼び出す。
これらのライブラリにより、Ruby や Crystal を用いる研究者や開発者は、外部コマンドを介さずに
ゲノムデータをプログラム内で処理できる。

# 必要性

ゲノムデータに対する多くの定型処理には、専用のコマンドラインツールが提供されている。
しかし、研究固有の解析では、複数のフィールドの組み合わせに基づいてレコードを選別・集計
したり、レコードを対話的に調べたり、結果を独自のデータ構造に保持したり、処理を別の
ライブラリと連携させたりする必要が生じる。このような処理は、既存ツールのオプションだけでは
表現できず、独自のスクリプトやプログラムを必要とすることがある。
HTSlib は、ファイル形式の解釈、圧縮、インデックスを用いた検索などを C API として提供する。
これらの機能を高水準言語から安全に扱うには、C 関数を呼び出すだけでなく、HTSlib の
ファイル、ヘッダー、レコード、およびそれらの生存期間を、各言語のデータモデルに対応づける
必要がある。

Python、Nim、Rust、C++ には、`pysam`、`cyvcf2`、`hts-nim`、
`rust-htslib`、`vcfpp` など、成熟した HTSlib インターフェースが存在する
[@pysam; @Pedersen2017cyvcf2; @Pedersen2018htsnim; @rust_htslib;
@Li2024vcfpp]。ただし、これらは各言語向けのインターフェースであり、Ruby や Crystal の
プログラムから直接利用できない。Ruby では、BioRuby のプラグインである
`bio-samtools` が、SAMtools を利用したアラインメント処理、pileup、変異解析、可視化の
高水準インターフェースを提供してきた [@Goto2010BioRuby;
@RamirezGonzalez2012BioSamtools; @Etherington2015BioSamtools2]。これに対し、
`ruby-htslib` は単体の HTSlib ライブラリに直接接続し、アラインメントとバリアントのファイル、
ヘッダー、レコードを、Ruby で解析プログラムを構築するための構成要素として提供する。
`hts.cr` は、同じ HTSlib の機能を Crystal の FFI、静的型システム、および
ネイティブコンパイルを通じて提供する。これにより、処理の中心部分を別の言語で実装せずに、
ストリーミング型のバイオインフォマティクスツールを記述できる。両ライブラリは、HTSlib の
機能を各言語の慣習に沿った形で組み合わせられるようにする。

# ソフトウェア設計

両ライブラリは、HTSlib のファイル、ヘッダー、レコードを、共通のレコード指向
オブジェクトモデルで表す。このモデルはネイティブリソースの生存期間を管理し、走査中に
借用する値と、その後も保持できる値を区別する。`Bam` は SAM/BAM/CRAM、`Bcf` は VCF/BCF の
ファイルを表し、それぞれが対応する `Header` を保持する。ファイルオブジェクトの `each` は
`Record` を一件ずつ返し、走査中は同じオブジェクトとネイティブバッファを使い回す。この方法は
ファイル全体をメモリに展開せず、割り当てを抑えられる一方、イテレータが次に進んだ後も
レコードを保持するには複製が必要となる。レコードのフィールドは Ruby または Crystal の
メソッドから参照・更新でき、アラインメントの補助タグとバリアントの INFO・FORMAT フィールド
は型付きの値として扱われる。領域検索と書き込みにも同じファイル、ヘッダー、レコードの
オブジェクトを用いる。

アクセス単位が異なる操作は、この共通モデルに無理に当てはめない。インデックス付き FASTA は
参照配列の一部を取得する `Faidx`、Tabix で索引付けされたテキストファイルは指定領域に重なる
行を返す `Tabix` として表す。pileup は別のファイル形式ではなく、`Bam` から得られる位置単位の
ビューであり、参照配列上の位置とそこに重なるアラインメントを列挙する。各ファイルオブジェクト
はブロック付きで開くことができ、ブロックの終了時にファイルが閉じられ、ネイティブリソースが
解放される。

このオブジェクトモデルを共有する一方、借用した値を公開し、結果を保持する仕組みには、
各言語の慣習を反映する。`ruby-htslib` の C 拡張は、HTSlib のポインターを型付きの Ruby
オブジェクトに格納し、対応する解放関数をガベージコレクタに登録する。走査ではネイティブの
レコードバッファを使い回し、保持する必要のあるレコードやフィールドは独立した Ruby
オブジェクトにコピーする。BCF の FORMAT フィールドは、再利用されるバッファの借用ビューを
通じて、コピーせずに参照することもできる。したがって、値を Ruby の配列や文字列として
保持する方法と、借用した値を走査中に処理して割り当てを抑える方法を用途に応じて選択できる。

`hts.cr` は、HTSlib のポインターを Crystal の静的型付きオブジェクトで包み、借用データと
所有データの区別を型とブロックの有効範囲で表現する。ネイティブバッファは、ブロック内だけ
有効な `Slice` 値や借用ビューとして参照でき、プリミティブ値のイテレータは、中間的な配列や
文字列を生成せずにフィールドを処理できる。走査後も必要な値だけをコピーすることで、ヒープ
への割り当てとガベージコレクションの負荷を抑える。この設計は、Crystal の
ネイティブコンパイルと組み合わせることで、ストリーミングツールにおける HTSlib データの
効率的な逐次処理を可能にする。

# 性能評価

各ライブラリの実行時オーバーヘッドを調べるため、同等の処理を C、`hts.cr`、
`ruby-htslib` で実装し、スループットを比較した。三つの実装はいずれも同じ HTSlib
（1.22.1-51-gcd2a6f61）を使用し、Ubuntu 26.04 LTS 上でシングルスレッドで実行した。
C の基準実装は GCC 15.2.0（`-O2`）、`hts.cr`
0.4.0 は Crystal 1.21.0（LLVM 20.1.8、`--release`）、`ruby-htslib` 0.6.0 は
Ruby 4.0.6 でビルドした。したがって、この比較は、HTSlib 自体の違いではなく、
言語境界と各 API のデータ表現に伴うコストを反映する。

評価には、2 Mbp の参照配列にアラインされた 100 bp のシングルエンドリード 300,000 件を
含む BAM（平均深度約 15 倍）と、20 サンプル、50,000 サイトからなり、GT、DP、AD、GL の
FORMAT フィールドを含む BCF を合成して用いた。BAM は座標順にソートし、両ファイルに
インデックスを作成した。領域検索と pileup の対象は、14,902 件のリードが重なる 100 kb の区間
（`chr1:500,000-600,000`）とした。pileup では塩基品質の下限を 13 とし、
マッピング品質によるフィルタリングは行わなかった。各ワークロードを 5 回実行し、表には
スループットの中央値を示す。初回の実行後、入力データ全体が OS のページキャッシュに収まった。
スクリプトは `benchmark` ディレクトリに収録している。

| pileup の塩基カウント | 6,792,000 columns/s | 4,846,000 columns/s | 140,000 columns/s |

レコードの逐次走査、整数値の FORMAT フィールドへのアクセス、領域検索では、`hts.cr` の
スループットは C の 94〜107% であった。サンプルごとの GT を文字列に変換する処理では
C の 88%、FORMAT/DP・AD の走査では 61%、pileup の塩基カウントでは 71% であった。
ネイティブバッファを直接処理できる経路では C に近い性能が得られ、文字列の生成や
高水準のビューを介した値の走査には追加のコストが伴うことを示している。

`ruby-htslib` は、逐次走査と領域検索で C の 45〜67% のスループットを示した。FORMAT
フィールドや pileup の処理では差が大きく、C に対するスループットは 2〜7% であった。
FORMAT/GT の整数走査と FORMAT/DP・AD の走査には、割り当てを抑えるイテレータまたは
借用ビューを用いたが、Ruby の値への変換とブロック呼び出しはレコード内の値ごとに発生する。
GT の文字列変換と pileup では、独立して保持できる値を返す `genotype_strings` と
`each_base_counts` を用いており、コピーとオブジェクト生成のコストも含まれる。なお、
三つの実装はすべて同じレコード数を処理し、pileup で数えた塩基の総数も 1,017,916 で
一致した。

この評価は、各言語の優劣を一般化するものではなく、本稿で提供する API の代表的な実行経路を
比較したものである。結果は単一の実行環境と一つの合成データセットに基づくため、実データを
用いたアプリケーション全体の実行時間や、大規模ファイルに対する性能を必ずしも予測するもの
ではない。

# 研究への影響

BioCrystal では `hts.cr` が、式を用いて BAM/CRAM ファイルをフィルタリングする
コマンドラインツール `bam-filter` と、libui-ng を用いた BAM ビューア `bamboo` に
利用されている [@bam_filter; @bamboo]。
